# Entry 11: Game loop. Player moves. Charlie hunts.

## What happened

The floor looks like a floor now.

Not a height map. Not a proof that Sobel derivatives work on a gradient. An actual floor: wood, different-width planks, grooves catching the light at a different angle than the plank faces. I spent probably a minute just moving the mouse across it before I touched the game logic. There was something satisfying about a room existing in there.

Then I added the player. Then I added Charlie. And then there was a specific moment when I watched his shadow grow. I was very proud ngl.

---

## The floor

The radial hill from Entry 05 was always a placeholder. A smooth mound that the Sobel filter could find edges in. It proved the pipeline. It doesn't look like anything.

Replaced it with planks. 32px tall. 2px dark groove between each one. Each plank gets a slightly different brightness: `randomSeed(7)` draws from a range of 175 to 200. The seed is fixed so the pattern doesn't change between runs.

```javascript
function buildHeightMap() {
  const img         = createImage(960, 540);
  const plankHeight = 32;
  const grooveWidth = 2;
  const numPlanks   = ceil(img.height / plankHeight) + 1;
  img.loadPixels();
  randomSeed(7);
  const plankBrightness = [];
  for (let p = 0; p < numPlanks; p++) {
    plankBrightness[p] = floor(random(175, 200));
  }
  for (let y = 0; y < img.height; y++) {
    const plankIndex = floor(y / plankHeight);
    const ty         = y % plankHeight;
    const brightness = ty < grooveWidth ? 140 : plankBrightness[plankIndex];
    for (let x = 0; x < img.width; x++) {
      const i           = (y * img.width + x) * 4;
      img.pixels[i]     = brightness;
      img.pixels[i + 1] = brightness;
      img.pixels[i + 2] = brightness;
      img.pixels[i + 3] = 255;
    }
  }
  img.updatePixels();
  return img;
}
```

The Sobel shader didn't change. Not a single character of GLSL. Same math, different texture fed into it. The grooves are brightness 140 against plank faces at 175–200: that sharp height transition is what the Sobel kernel finds. It converts it into a normal pointing nearly sideways, so groove edges catch the point light at a steep angle and read as physical depth. Plank faces catch it as a flat surface.

I knew separating the height map from the lighting math was right from Entry 06. I didn't believe it until I swapped the texture and everything worked without touching the shader.

## Player movement

Player position stored in UV space (0→1), same coordinate system as every shader uniform. That was the decision. It means `playerPos.x` goes directly into `uMouse` and `uLight` with no conversion. The shaders already speak UV. The player just had to speak it too.

```javascript
if (keyIsDown(65)  || keyIsDown(LEFT_ARROW))  playerPos.x -= PLAYER_SPEED;
if (keyIsDown(68)  || keyIsDown(RIGHT_ARROW)) playerPos.x += PLAYER_SPEED;
if (keyIsDown(87)  || keyIsDown(UP_ARROW))    playerPos.y -= PLAYER_SPEED;
if (keyIsDown(83)  || keyIsDown(DOWN_ARROW))  playerPos.y += PLAYER_SPEED;
playerPos.x = constrain(playerPos.x, 0.01, 0.99);
playerPos.y = constrain(playerPos.y, 0.01, 0.99);

myShader.setUniform('uMouse', [playerPos.x, playerPos.y]);
shadowShader.setUniform('uLight', [playerPos.x, playerPos.y]);
```

The 0.01 margin on constrain is a small thing. Without it the light sits exactly on the canvas edge and the attenuation formula produces a flare in the corner. Caught it immediately: top-left of the screen went wrong on the first run.

Previously `uMouse` was `[mouseX / width, mouseY / height]`. Now it's `[playerPos.x, playerPos.y]`. The shader receives exactly the same type of data. It doesn't know anything changed.

## Charlie

Two lines of actual AI logic:

```javascript
const dx   = playerPos.x - charliePos.x;
const dy   = playerPos.y - charliePos.y;
const dist = sqrt(dx * dx + dy * dy);
if (dist > 0.001) {
  charliePos.x += (dx / dist) * CHARLIE_SPEED;
  charliePos.y += (dy / dist) * CHARLIE_SPEED;
}

shadowShader.setUniform('uCharlie', [charliePos.x, charliePos.y]);
```

The `dist > 0.001` guard is not optional. First test run: Charlie spawned at the same position as the player. `dist` was zero. `dx / dist` (division by zero): the shader received NaN and went completely white. Spent ten minutes looking in the GLSL before realising the problem was in JavaScript. "Shadow going white" reads as a fragment shader problem. It wasn't.

First speed I tried was `CHARLIE_SPEED = 0.003`, same as player speed. He caught me in about eight seconds. No tension. Just: you move, he moves just as fast in the same direction, you hit a wall, he arrives. Dropped it to `0.0008`. Now there's time to understand what's happening, time to feel the shadow getting bigger, time to make a decision that turns out to be wrong. That's the space the game lives in.

## The shadow radius

Used to be hardcoded to `0.08`. Now:

```javascript
const shadowRadius = constrain(map(dist, 0.05, 0.5, 0.18, 0.05), 0.05, 0.18);
shadowShader.setUniform('uRadius', shadowRadius);
```

When I tested it I didn't press any keys. Just started the build and watched Charlie approach from the corner with me standing still. The shadow grew. Slowly first, then faster as dist dropped below 0.2. The vignette at the screen edges deepened because the bloom was darkening along with the lit area. The room got smaller.

I wrote `map(dist, 0.05, 0.5, 0.18, 0.05)`. That's the whole horror mechanic. One line.

## Why the player has no sprite

The player is the light. There's no dot on screen, no character, no crosshair. When you move, the entire environment shifts: the lit floor rotates around you, the shadow changes direction, the vignette redraws with you at the center.

A sprite would make you steer a thing. Being the light makes you inhabit a space. The whole visual system responds to where you are. Adding a dot on top of that would make the experience smaller. The absence is the point.
